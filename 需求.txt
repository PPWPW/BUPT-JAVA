大作业：揭棋对弈程序设计
分组：
4-6人一个小组完成，小组必须有一名组长协调组织。完成大作业提交实验报告必须写明成员分工及按百分比划分的贡献度。
AI辅助：
必须使用AI辅助分析设计、编程测试。
内容：
每个小组可以选择下面设计对弈程序和AI博弈两个部分之一实现，如果一个部分没有小组选择，教师随机强制3个小组做另外一个部分：
设计一个揭棋对弈程序:
支持两个客户端通过服务器真人对弈。服务器和客户端通过TCP Socket通信，都必须能禁止错误着法。但是不考虑不应将这种错误，此时对方可直接吃掉将帅获胜（如果走不出来也不自动判胜）。
这里必须定义棋谱记录方法：
棋盘从上到下第一行到最后一行，坐标为9-0十个数字，从左到右为a到i共9列，先手方在棋盘下方，后手方在上方（客户端不一定如此设置上下，可以是己方在下）。每一步就是两个坐标：原位置（source）和新位置（destination）。每个棋子的第一步还要加上翻出来的棋子类型（type），此时服务器生成随机数来确定究竟翻出什么子。
服务器可以自动记录棋谱。
服务器启动后一次接受双方客户端的走子信息（每一步为一个move对象，包括三个属性source、destination和type（后续步法type可以有，也可以空着），还有一个时间戳（记录客户端和服务器发送走子信息时间）），另外启动计时器判断超时：
Class Move{
		Private String source;			//例如“b3”
		Private String destination;     //例如 “b4”
		Private Integer type;         // 例如 1
// type: 0=将帅， 1=车， 2=马， 3=炮， 4=兵卒， 5=士， 6=象
		private long turnStartTime; // 保存开始的时间戳（毫秒），计算超时可以适当考虑网络延迟。比如加5s计算。
}
以服务器端时间戳为准，客户端可能造假忽略。
客户端不需要过分重视图形用户界面的美化。
可选：一台服务器上可以同时支持多盘对弈。

使用AI博弈：
可以借用第一部分的图形界面进行检测（但要自己集成），也可以没有图形界面，只是发送和接受走子信息进行对弈。
运气成分与评估：局面评估必须将暗子的“数学期望值”纳入考量。你算出的“最佳”走法，实际效果依赖翻出的随机结果。
巨大的搜索树：AI每多思考一步，需要计算的可能局面数量会急剧膨胀，对算法效率要求极高。博弈的关键在于采用例如基于Alpha-Beta剪枝的揭棋算法在进行正确的局面判断后，忽略掉大量更加劣势的局面。
评估函数设计：除了象棋的评估，如何为一个未翻开的暗子做基于概率的分析，准确赋值其价值，是决定AI棋力的关键。
不同小组同学可以自行博弈，并将胜负情况公开报告，获胜多者成绩适当提高。有兴趣同学可以和自己的AI程序博弈看看你们的程序是否能战胜没有多少经验的棋手。
建议使用AI agent实现，每个agent其实就是一个对象。

强制要求：
	采用面向对象程序设计，至少需要有5个以上领域类。
	服务器和客户端可以互操作，比如第一组的服务器可以连接第二组的客户端。

问题反馈和接口定义：
	有问题及时联系老师，如需要老师认可基础上定义公共接口各个小组都遵照执行。
	本题目定义应该是不完整的，先提出问题并完善的小组将有最多额外8分加分。

附：揭棋的规则
（有不明了之处，可以在网上查找补充，不过需要经过老师认可后全体同学都遵照设计）
基于中国象棋但有所扩展，核心在于棋子的明暗机制与走子变化。
🎲 开局与翻子：核心机制
设置：棋盘和棋子与中国象棋完全一样。开局时，除了双方的“将”和“帅”正面朝上摆在自己九宫的原位，己方其余15枚棋子（如车、马、炮、兵等）全部背面朝上、随机打乱后，摆放在己方棋盘的原始位置上。背面朝上的棋子称为“暗子”，正面朝上的称为“明子”。
走子与翻子：玩家轮流走棋。
o移动：走到某个暗子时，必须按照它当前所在位置对应的中国象棋棋子的规则来移动。
o翻开：暗子移动或吃子后，必须立即翻开，变成“明子”。翻开后，它的移动规则就由其真实身份决定，该身份也会一直保持不变。
o翻面选项：除了通过移动翻开，玩家还可以选择在当前回合不移动任何棋子，只把棋盘上的一个暗子原地翻开（该操作即为一回合）。
吃子：和中国象棋一样。
o吃暗子一方知道对方被吃什么子。
o暗子被吃子一方不知道吃掉的是什么子。
🚀 核心规则
特殊强化：变为明子的“士”和“象”，棋盘活动范围大大加强。
o士（仕）：可以离开九宫，并且可以过河参与攻杀，吃子时依然斜走一格。
o象（相）：同样可以过河，大大增强了防守和进攻能力。
o需要留意的是，“塞象眼” 和 “蹩马腿” 的规则与常规象棋一致，依然有效。
⚖️ 胜负与和棋判定
胜负：基本与象棋相同。
o失败：被将死、困毙、认输或超时的一方判负。针对AI下棋超时可定义为每步1分钟，但是因为网络延时可能需要采用某种时间戳设置。
o胜利：失败的对方获胜。
和棋：揭棋引入了特定规则来防止僵局。
o40回合无吃子：如果双方连续走40步棋都没有发生吃子，则自动判和。
长将/长捉：连续多次重复将军或捉子会被判负。主流规则允许最多6回合。但是兵卒长捉判和。

利用AI设计较大规模程序的方法：
基本概念：
一步到位不可行：
利用AI编写较大规模的程序，完全依赖于一次性对话生成全部代码是不可行的（受上下文长度、逻辑连贯性、错误累积等限制）。
划分模块，逐步完成：
把AI当作一个能力很强但需要持续引导的协作者
一次完成一个部分。
分析设计的过程：
不是让AI独立完成，而是人机协作、逐层细化。

需求分析与架构设计（必须做，且要分层次）
1.1 让AI帮助澄清需求
用自然语言向AI描述你想解决的问题（不必完美）。
让AI反向提问，例如：“你希望系统支持哪些功能？”“用户是谁？”“数据量大约多大？”“性能要求如何？”
让AI输出一份需求清单和边界条件，你进行审核和补充。
1.2 让AI参与模块划分与架构选型
提问：“根据上述需求，请建议一个大致的模块划分和主要的技术栈选择（如Web框架、数据库、中间件）。”
AI会给出分层方案（如前端/后端/数据库、微服务或单体、核心组件等）。
你可以追问：“这个架构的优缺点是什么？”“有没有更简单的替代方案？”
输出物：系统架构图（文字描述或让AI生成Mermaid）、模块列表、模块间接口约定。
1.3 让AI帮助设计数据模型与核心接口
提问：“请设计本系统的核心数据表结构（如果是数据库）或主要类的字段及方法。”
AI会生成初步的UML类图或SQL DDL。
你检查并调整（AI可能做出不符合业务实际的假设）。
为什么必须先分析和设计？
因为较大规模的程序需要清晰的蓝图，否则AI生成的代码会彼此矛盾、重复或缺失关键逻辑。AI在全局推理上有限制，但擅长将人类的宏观决策细化为结构化方案。

拆分任务，迭代生成代码（核心技巧）
2.1 将项目拆解为“可独立验证的小任务”
例如：不要求AI一次完成“用户注册+登录+密码找回”，而是拆成：
o任务1：定义User实体和数据库映射
o任务2：实现注册接口（存储加密密码）
o任务3：实现登录验证并返回token
o任务4：实现密码找回的发送邮件功能
每个任务规模控制在200~500行代码以内，AI更容易正确生成。
2.2 为每个任务提供充分的上下文
不要只说“写一个登录接口”，而要提供：
o已有实体类的定义（让AI复制或引用）
o已有的工具类（如JWT util）
o期望的输入输出示例
如果上下文过长，可以先用AI生成接口定义（函数的签名、预期的入参出参），确认后再生成实现。
2.3 编写测试用例驱动AI
让AI先生成单元测试（描述测试场景），然后生成实现代码，使测试通过。
测试也是文档，能帮助AI理解预期行为。
2.4 迭代集成，及时纠偏
将AI生成的各模块代码放入IDE中编译运行。
遇到编译错误或逻辑错误，不要直接自己改，而可以把错误信息和相关代码片段发回给AI，让它修正。
对于复杂的bug，可以问AI：“这个错误可能是因为什么？请给出3种可能的原因，并逐个排除。”

AI无法替代的工作（必须由人把控）
任务	为什么AI做不到
真正的需求理解	AI只能根据你的描述推测，无法理解业务上下文和政治因素
架构的关键权衡	例如选择Kafka还是RabbitMQ，需要结合实际运维能力和成本
安全与合规	AI可能给出不安全的默认配置（如密码明文传输）或忽略GDPR要求
代码审查与重构	AI生成的代码可能凑合能用但难以维护，需要人工重构
部署与监控	需要编写Dockerfile、配置CI/CD、设置告警，AI最多提供模板

四、推荐的具体工作流（以开发一个Web后端为例）
1.对话AI进行需求分析：
“我需要一个图书管理系统，支持用户借阅、归还、查询库存。请帮我列出所有功能点和潜在的非功能需求（并发、安全性）。”
2.对话AI进行技术选型：
“根据以上需求，推荐使用Spring Boot + JPA + H2（开发）还是其他？请给出理由。”
3.让AI生成项目骨架：
“请生成一个Spring Boot项目的pom.xml，包含Web、JPA、Lombok依赖，以及主类。”
4.按模块顺序生成：
o先生成实体和Repository
o再生成Service（业务逻辑）
o最后生成Controller
o每步都要求AI同时生成对应的单元测试
5.集成与调试：
将代码放入IDE，运行测试。失败时把错误堆栈贴给AI，要求修复。
6.让AI帮助重构：
代码工作后，问：“请检查这个Service类，是否有违反单一职责原则的地方？建议如何拆分？”
7.生成文档与部署配置：
“请根据上述代码，写一个README介绍如何运行，并生成Dockerfile。”

关于“是否需要先请AI分析和设计”
需要，且必须。
但不是让AI独立完成分析和设计，而是人提出高层想法 → AI结构化、补充细节 → 人审核修正 → AI继续细化这样一个螺旋式协作过程。
如果你跳过分分析和设计，直接让AI生成大量代码，会出现：
模块间接口不匹配
重复实现同一功能
无法扩展的硬编码
缺失非功能需求（如并发控制、事务边界）
正确顺序：
人提想法 → AI帮助整理需求 → 人拍板 → AI拆分任务→人确认任务 →AI协助设计 → 人确认设计 →生成代码 → 人测试反馈 → AI修正 → 集成 → 重构 → 部署。
最终，AI是你的高级结对程序员，而不是项目经理或架构师。架构师的决策、需求边界和关键验收标准，仍然需要你来掌握。
